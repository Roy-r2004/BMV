## 3. What still blocks two of three — and it is the same bug, one layer up

Both failures are one finding:

    journey_no_detail_route
    Browse the collection: no detail route is declared, so items cannot be opened
    153  src/pages/CelebrationCakesPage.tsx  /celebration-cakes
    156  src/pages/BikeRangePage.tsx         /bikes

**It is true.** Read off the shipped routers:

    153  App.tsx serves  /  /product  /checkout  /celebration-cakes  /admin/dashboard  *
    156  App.tsx serves  /service-booking  /bikes  /  *

No param route, and no minted alias either. A visitor clicking a card on either grid lands on
`path="*"` and is redirected home. This finding is **newly visible**, not newly true: before 2c
the browse hop could not resolve on a renamed catalogue at all, so on 148 the whole journey came
back absent and nothing about that funnel was checked.

**Root cause, and it is this session's rule again.**
`product_kind._inject_blueprint_routes` (`backend/app/application/preview_app/product_kind.py:1188`):

```python
parent = _detail_parent_path(path)          # "/gallery/:id" -> "/gallery"
if parent:
    if parent not in existing_paths or any(...):
        continue                            # detail page never added
```

The storefront blueprint's detail page is `/gallery/:id`, so the gap-fill looks for a literal
`/gallery` in the table. 156's catalogue is `/bikes` and 153's is `/celebration-cakes`, so the
parent lookup misses and the detail route is silently skipped. That is a route literal
*referencing* a route — exactly what 2a/2b/2c removed from the emitters — surviving in the
planner. The fix has the same shape: resolve the detail blueprint's parent against the route
wearing `skeleton_id == "public-catalog"`, and hang the param off *that* path rather than off
`/gallery`.

Not done here. It is a fourth pipeline change with planner blast radius, discovered at the last
step of a four-step brief, and it deserves its own gate.

## 4. Two findings the trio turned up that nobody was looking for

**(a) `seed.cta.primaryHref` is an unvalidated route literal, and the sweep is blind to it.**
The mock writer sets it, and it invents paths:

| run | `cta.primaryHref` | `cta.secondaryHref` | declared? |
|---|---|---|---|
| 153 | `/reserve` | `/order` | neither |
| 156 | `/shop` | `/alerts` | neither |
| 157 | `/gallery` | — | no |

Six dead targets across three apps, and **`dead_link_occurrences` is 0 on all three**. The
journey sweep cannot see them: `_HREF_LITERAL_RE` (`capabilities/journey.py:60`) is
`(?<![\w-])["']?(?:href|defaultPath)["']?…`, and in `"primaryHref"` the `href` is preceded by a
word character, so the lookbehind blocks the match and the quoted-key arm cannot match either.
Widening the key alternation to `\w*[Hh]ref` finds all six. 157's is the joke of it: the model
wrote the literal `/gallery` into a hardware store's call-to-action.

The same blind spot exists in the scaffold's `cta` slot, which emits
`href: seed.cta?.primaryHref ?? "/contact#inquire"` — the census in
`tests/preview_app/test_route_literal_census.py` had to widen its own pattern with a `??` arm to
see it, and `/contact` is on that module's allowlist as the next slice.

**(b) Brand poison reached the seed copy.** 156's `mock.ts` carries
`"Ready for Business?"` — the `Brand`/`Business` fallback survived into generated copy on a run
whose brand name is Ridgeline Bike Works. `sync_mock_images` scrubs `brandName={"Brand"}` in
pages; it does not scrub brand fallbacks inside `seed`.

## Process notes

- **`requests.status` is not the run verdict.** It stays `new` when the pipeline *completes*, and
  becomes `failed` only when it raises. The verdict is
  `generated_pages -> preview_app -> status`. Polling the wrong column makes a finished run look
  like it is still going — it cost two ten-minute waits here. Confirmed against 146-151.
- **The reference image for a past run is recoverable.** `requests.reference_file_path` points
  into `bmv-api:/app/data/uploads/`; `docker cp` it out and a `file`-mode run can be repeated
  with the identical input.
- **`docker restart bmv-api` before measuring, every time.** `UVICORN_RELOAD=false` means the
  container holds the code it started with. Confirmed loaded by importing `booking_route`,
  `catalog_route` and reading the hop skeletons out of the running process.
- **The launcher must run inside the api image.** The host python has no `requests`; the
  `bmv-local-api` image with `--network host` reaches `127.0.0.1:8001`.
